# Localization

The runtime ships no translation engine. It knows one interface and resolves the locale of every
event; the catalogue is yours, or the one your application already has.

## Register A Translator

```php
use ChatFlow\I18n\ArrayTranslator;
use ChatFlow\I18n\TranslatorInterface;

$runtime->getContainer()->set(TranslatorInterface::class, new ArrayTranslator([
    'en' => ['greeting' => 'Hello, {name}', 'menu.title' => 'Menu'],
    'ru' => ['greeting' => 'Привет, {name}', 'menu.title' => 'Меню'],
]));
```

`ArrayTranslator` tries the requested locale, then its primary subtag (`en-GB` falls back to
`en`), then the fallback locale (`en` unless you pass another). A missing id is returned as-is, so
a forgotten translation is visible but never breaks a flow. `{name}` placeholders are filled from
the parameters.

## Reuse An Existing Catalogue

```php
use ChatFlow\I18n\SymfonyTranslatorAdapter;

$runtime->getContainer()->set(
    TranslatorInterface::class,
    new SymfonyTranslatorAdapter($symfonyTranslator, domain: 'messages'),
);
```

`SymfonyTranslatorAdapter` needs `symfony/translation-contracts` and passes parameters through
unchanged, so use the placeholder style of that catalogue (`%name%`). Any other library is one
class with one method.

## Resolve The Locale

```php
use ChatFlow\I18n\ChainLocaleResolver;
use ChatFlow\I18n\SessionLocaleResolver;
use ChatFlow\Middleware\LocaleMiddleware;

$runtime->middleware([
    new LocaleMiddleware(new ChainLocaleResolver(
        new SessionLocaleResolver(),      // the language the user chose
        new TelegramLocaleResolver(),     // the language the platform reports
    )),
]);
```

| Resolver | Answers with |
| --- | --- |
| `SessionLocaleResolver` | the stored preference, `$ctx->session()->get('locale')` |
| adapter resolvers | the language the platform reports (Telegram: `language_code`) |
| `ChainLocaleResolver` | the first non-empty answer of the resolvers it wraps |

Store the preference when the user picks a language:

```php
$runtime->onAction('lang:ru', static function (Context $ctx): void {
    $ctx->session()->set('locale', 'ru');
    $ctx->ack();
    $ctx->render(View::text($ctx->t('menu.title')));
});
```

Write your own resolver by implementing `LocaleResolverInterface`; returning `null` means "no
opinion" and passes the question to the next resolver in the chain.

## Translate

```php
$ctx->t('greeting', ['name' => $name]);
$ctx->t('greeting', ['name' => $name], 'en');   // explicit locale, ignores the resolved one
$ctx->getLocale();                              // what the middleware resolved, or null
```

`t()` throws `LogicException` when no translator is registered. Scenes, services and middleware
can also take `TranslatorInterface` in the constructor and translate outside a request.

## Rules

- The locale is request-scoped: resolved once per event, never stored on a scene.
- Message ids belong in the catalogue; a bot with two languages keeps no user-facing text in
  handlers.
- Views are built from translated strings. The runtime never translates anything on its own.
